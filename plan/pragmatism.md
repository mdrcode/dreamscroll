## Philosophy

Dreamscroll is an exploratory  project whose primary risk is **not** technical.
The primary risk is that the app isn't useful enough to justify its own
existence. Every hour spent hardening a race condition that only manifests
under multi-user concurrency is an hour not spent validating the core use case.

So: **we deliberately tolerate a set of known issues** in order to move fast on
product validation. This document is the ledger of those trade-offs, so that:

1. We don't rediscover them repeatedly and re-litigate whether they matter.
2. We don't forget them — each entry has a **revisit trigger** describing when
   it stops being acceptable.
3. We can tell the difference between "we didn't notice" and "we chose this."

**The bar for tolerating something:** it must be primarily a *throughput, cost,
or code-cleanliness* concern, with no severe negative user-facing effect. If an
issue can corrupt user data, leak another user's data, or silently lose work in
a way the user would notice, it does **not** belong here — it gets fixed.

**The bar for fixing something now:** it's cheap, unambiguous, and doesn't
distract from product work. (Several items below were fixed on exactly that
basis and are recorded as resolved for context.)

## How to use this doc

- When you find an issue, ask: *does this have a severe user-facing effect?*
  - **Yes** → fix it, or file it as a real bug.
  - **No** → add it here with a revisit trigger, and move on.
- When a revisit trigger fires, promote the entry to a real task.
- When you fix something, mark it resolved rather than deleting it — the
  history of what we chose to tolerate is itself useful.

## Tolerated trade-offs

### Concurrency

These are all "correct at one user, wrong under concurrency." They are the
largest category, and the least urgent, because the app is single-user today.

| Issue                                                                        | Effect                                                                                                                                                                                                                                      | Why tolerated                                                                                                                                                                                                                                                   | Revisit trigger                                                                                       |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **No idempotency guards in `logic/illuminate.rs` / `logic/search_index.rs`** | A retry re-calls the LLM and may re-embed. Raw and relational illumination output upserts by TaskRun `run_id`, so sequential retries replace earlier output; overlapping deliveries may still duplicate inference cost or race to write. A new settled run has a new `run_id` and its own row. | Duplicate calls are accepted for prototype velocity. The read path surfaces the latest illumination, while TaskRun-keyed upserts prevent duplicate result rows for sequential retries. | Duplicate LLM spend becomes noticeable, or overlapping attempts write stale results. |
| **An in-flight search-index task can miss a newer illumination**             | If re-illumination occurs while indexing is in flight, that task may have already loaded the prior illumination. Beacon refuses a duplicate in-flight index submission, so the vector can remain stale until another index run or backfill. | Requires overlapping re-illumination and indexing; normal new-capture flow enqueues indexing only after illumination persists. A dirty/version marker or deferred rerun would add coordination state for a narrow race.                                         | A stale vector is observed after re-illumination, or re-illumination becomes a common operation.      |
| **Attempt claiming is read-then-write** | Concurrent deliveries can both execute; racing reads can claim the same attempt number, while a later `InProgress` redelivery may increment it. | Cloud Tasks is at-least-once; there is no atomic claim or lease fencing workers. Duplicate work and status races are accepted for the prototype. | Concurrent duplicates cause noticeable cost, incorrect status, or user-visible result ambiguity. |
| **Status transitions are permissive** | A late attempt can overwrite a newer status or run-keyed raw/relational output because updates are not fenced by attempt. | Duplicate overlap is possible, but strict transition/fencing logic adds lifecycle complexity; accepted for the prototype. | Out-of-order delivery produces visible incorrect status or raw output. |
| **Entity snapshot order is not a presentation contract**                     | The latest-run query orders rows by entity, task type, and descending run for PostgreSQL `DISTINCT ON`, not by UI presentation needs.                                                                                                      | Current consumers need the latest row per entity/task type, not a custom cross-entity order.                                                                                                                                                                    | The UI requires a different explicit ordering.                                                       |

> **Note on the removed guards:** the `illuminate` and `search_index` idempotency
> guards were deleted outright. A "skip if already illuminated" check silently
> no-ops every rerun (reporting success while doing no work), so keeping it meant
> deriving the run number from the illumination count — machinery that didn't
> reliably prevent the duplicate it existed for. Removing is simpler and makes
> reruns work by construction. A `UNIQUE(capture_id)` constraint on
> `illuminations` is *not* wanted: multiple illuminations per capture is the
> intended outcome of reruns.
>
> **Note on illumination visibility:** reruns append rows, so `InfoMaker` now
> collapses `illuminations` to the highest `id` — `CaptureInfo.illuminations` has
> at most one entry. This is enforced in one place rather than relying on loader
> order (SeaORM orders related rows by primary key *ascending*, so `.first()`
> would have returned the oldest).

### Cost / throughput

| Issue                                                                                                 | Effect                                                                                                                                | Why tolerated                                                                                | Revisit trigger                                                               |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **`api/user/client.rs` swallows `Beacon.new_capture` errors** (logs a warning, still returns success) | A capture can be uploaded but never illuminated/indexed, with no user-visible signal.                                                 | The upload itself succeeded, which is what the user cares about. Failure is visible in logs. | A user notices a capture that never got illuminated.                          |
| **`CloudTaskQueue` URL configuration is deployment-specific**                                         | The same `TASK_WEBHOOK_BASE_URL` must point to a reachable local host or public production origin, depending on the selected backend. | The queue backend is mutually exclusive, and one setting avoids duplicate configuration.     | A deployment needs separate task targets or URL validation becomes important. |
| **Inference usage persistence is best-effort** | Database insert failure or process termination can lose usage; successful outputs may have NULL `inference_meta_id`. Only TaskRun-backed requests are recorded, so direct CLI inference and inline query embeddings are excluded. | One shared warning-and-continue insert avoids retrying billable inference for bookkeeping. No recovery queue, outbox, or accounting-only TaskRuns. Raw usage remains available when the insert succeeds. | Missing usage becomes material for budgeting, or synchronous-query accounting is needed. |
| **Failed inference calls record no usage row** | `inference_metas` is written only after the provider call returns, so a timeout, 500, or cancelled request leaves no duration or token row. Retries re-run inference, and the spend on those failures is visible only in billing and as queue failure timings (`dreamscroll_api queue throughput`). | A failure-side usage row would need a new write path at the client boundary; the queue failure histogram already exposes how often this happens, which is enough while latency is being investigated. | Failed/timeout inference spend becomes material, or usage reporting must reconcile with provider billing. |
| **Inference metadata cutover requires manual cleanup** | The operator drops obsolete metadata tables and removes old required bookkeeping columns from `illumination_raws`, or drops/recreates affected prototype tables, before running explicit schema sync. Historical bookkeeping may be discarded. | Prototype data needs no migration. Destructive cleanup stays manual rather than accumulating one-off DDL in `sync_schema`; model sync remains additive. | Historical metadata must be preserved, or staged/rolling schema compatibility is required. |
| **Historical inference JSON is not reclassified** | Rows written before request/provider separation may still contain response details in `params`; `provider_metadata` defaults to `{}` on existing rows. Data from the earlier version-4 provider-details column is not transferred. New rows use request-only params and separate provider metadata. | Prototype bookkeeping needs no data migration or compatibility branch; obsolete columns remain operator-owned cleanup. | Historical metadata must obey the new semantic contract for analysis. |
| **Related-capture previews are recomputed per detail-page view** | Each `/capture/{id}/related/previews` request fetches the source embedding and runs one vector search; nothing is cached or persisted. | The gallery is client-fetched after the detail page renders, so it never blocks first paint; results are cheap at prototype scale and staleness would be a new invalidation problem. | Related previews dominate detail-page latency or vector-search spend, or results must be stable across reloads. |
| **Entity-type listing is unbounded** | `get_entities_by_type` returns every matching row for the user with no limit or pagination, and the CLI taxonomy review relies on that shape. | Single user, and the endpoint exists for taxonomy review rather than interactive browsing. | The listing grows past a few hundred rows or gains a UI consumer. |
| **Thinking-level model compatibility is provider-validated** | The CLI/API accepts Gemini's four documented levels, but a particular model may reject a level it does not support. Omitting the override preserves provider defaults. | Avoid a stale local model-support matrix and silent effort downgrades while comparing inference behavior. | Provider validation errors become common enough to justify model-specific preflight checks. |

### Security / defense-in-depth

| Issue                                                                          | Effect                                                                                                                                                                                                                             | Why tolerated                                                                                                                                                                       | Revisit trigger                                                                                       |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **Task payload fields are not cross-checked against the stored run identity** | A malformed or stale Task can pair an existing `(logical_id, run_number, run_id)` with a different `entity_owner_id`, task type, entity, or payload; execution and SSE metadata could disagree with the submitted work. | Queue payloads are produced internally and the webhook has OIDC protection. Cross-checking payload fingerprints would add task-framework work while we validate the app's use case. | Enable another producer or observe a mismatched status/event. |
| **Worker update for a missing task-run row is warned and ignored**             | A stale or malformed TaskRun may execute without a matching status row; no SSE status event is sent for its update.                                                                                                               | TaskRun payloads are internal and authenticated; ignoring avoids retrying work whose tracking row is absent, while the warning keeps the inconsistency visible.                   | Observe a missing-row warning, or change stale-delivery policy.                                       |
| **Admin/internal Task owner is trusted** | A trusted admin or internal producer could set `Task.entity_owner_id` differently from the target row, misattributing status. | User submissions require the owner's Context; admin backfill reads the capture owner from the database; internal follow-ups copy the parent Task owner. Admin/internal producers remain trusted. | Add admin flows that accept arbitrary owner IDs, or observe a task/status owner mismatch. |
| **`TaskRunTracker::insert_run` is check-then-act**                             | Two concurrent submissions can both choose the same per-logical `run_number`.                                                                                           | The `(logical_id, run_number)` unique index arbitrates: the loser's insert becomes `Ok(false)`, so correctness does not depend on the read.                                    | If the refusal path is logged as an unexpected error, or a second user is added.                      |
| **Webhook OIDC verification depends on Google's JWKS endpoint**                | A cold instance or key rotation can add latency or temporarily fail webhook authentication if Google's certificate endpoint is unavailable. The Google crate caches each key for one hour, but does not retry a failed JWKS fetch. | `google-cloud-auth` provides maintained key fetching/caching; custom retry/backoff infrastructure is outside the MVP.                                                               | Authentication latency or task retries become operationally noticeable.                               |

### Operational

| Issue                                                 | Effect                                                                                                                                    | Why tolerated                                                                                            | Revisit trigger                                                                         |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **No retention / vacuum policy on `task_runs`** | The table grows forever. Note the run dimension means a reran task keeps *all* its rows, so growth is per-run rather than per-task.       | Tiny table, single user.                                                                                 | Row count becomes non-trivial, or query latency degrades.                               |
| **No heartbeat / timeout for stuck tasks**            | A task enqueued but never picked up (queue dropped, worker crash) stays `Queued` forever and looks active.                                | Requires an actual lost task, which hasn't happened.                                                     | First observed stuck task, or when the SSE UI makes it visible to the user.             |
| **No queue-level reconciliation**                     | The database cannot independently verify that a `Queued` row has a corresponding Cloud Task, or recover from an ambiguous enqueue result. | The app is small and the status row plus logs are sufficient operational visibility for the MVP.         | A task is observed stuck or missing, or Cloud Tasks/DB state needs auditing.            |
| **SSE heartbeat timeout is heuristic** | A delayed or suspended client can restart a healthy stream after 50 seconds without a heartbeat, adding a request and catch-up query. | The application heartbeat tells JavaScript that SSE events are still arriving; transport-level activity alone does not prove the browser received events. Background delivery remains best-effort. | Reconnects are observed on healthy delayed clients, or the 50-second detection window proves too long. |
| **SSE catch-up skips captures that already have an illumination** | Reloading a page during a re-illumination can miss the in-progress progress bar until the terminal event arrives. | Catch-up would otherwise query latest TaskRun state for every rendered capture on every page load and SSE connect. The reload-during-rerun flow is rare enough not to justify that DB load. | Reloads during reruns become common, or in-progress state during reruns becomes a product requirement; then batch/index the catch-up query. |
| **Blended feed treats `limit` as a per-source bound** | A blended timeline can return up to twice the requested limit (captures + sparks). | `limit` is currently an internal read bound; no UI exposes it, and total-feed semantics belong with the planned feed architecture work. | The feed gets explicit page-size/pagination controls, or membership/ordering is redesigned. |
| **Composite index on `task_runs` deferred**        | The entity snapshot query filters by user, entity type, and IDs, then selects the latest run per task type; only a single-column `entity_id` index exists. | Single-user app, tiny table. | Query latency degrades, or the table grows past a few thousand rows. |
| **Local queue shutdown is abrupt**                    | Dropping the final `LocalTaskQueue` handle aborts its dispatcher and drops pending in-memory tasks.                                       | The local backend is only for development and tests; production durability comes from Cloud Tasks.       | Local development needs restart-safe work or graceful shutdown testing.                 |
| **`submit_inner` records status before enqueueing**   | A process crash or ambiguous backend failure can leave a row at `Queued`; definite enqueue failures are changed to `SubmissionFailed`.    | DB-first submission avoids untracked tasks and duplicate execution; reconciliation can wait for the MVP. | A task is observed stuck or missing, or enqueue ambiguity becomes operationally costly. |
| **No explicit Gemini inference request timeout** | A stalled Developer API or Vertex call can keep an illumination worker occupied until the outer request/task deadline. | Defer client timeout behavior while validating the product; rely on existing outer deadlines for now. | A hung Gemini request causes task retries, duplicate spend, or delayed illumination; then set and test a client timeout shorter than the worker deadline. |
| **Undecodable notifications are skipped** | A malformed or future-schema NOTIFY payload is dropped; that hint never reaches clients and is only recovered by the next catch-up on reconnect. | The stream is best effort, and killing the fan-out loop for one bad payload would starve every user on the instance. | A real event kind is observed being dropped in practice. |
| **Backfill pumping can temporarily starve lower IDs** | A descending-ID batch occupied by live in-flight tasks is refused and remains eligible, so lower IDs can wait. | Live contention is expected to be short-lived and isolated; keep manual bounded pumps without cursor/scan-ahead/filtering machinery. | Contention or stuck live tasks persistently prevent progress. |
| **Backfill status counts actual runs, not expected workflow edges** | Beacon descendants inherit the ID, but refusal against unrelated live work creates no tagged child; aggregates cannot prove all expected descendants completed. | Avoid a dependency ledger and deferred follow-up scheduling. Same-backfill logical children are deduplicated, not counted per parent. | Operators need guaranteed end-to-end workflow completion. |
| **Backfill IDs and progress are developer-managed** | Reusing an ID after changing its definition or deleting tagged TaskRuns can invalidate progress. Failed tagged runs are not automatically replaced. | Stable literals and retained TaskRun rows avoid definition fingerprinting, migrations, and a per-target table. | Frozen membership, automatic recovery, or progress retention management becomes necessary. |
| **A backfill's "dry" record is an observation, not a coverage claim** | `backfills.dry_since` says a pump found no unsubmitted targets. It cannot prove every descendant was submitted or that any of them succeeded, and new input clears it. | The work graph has no declared edge set — handlers create children at run time — so completion is a submission-stream fact. Outcomes stay in `status`/`failures`. | Operators need a guaranteed total or an automatic end-to-end completion signal. |
| **Persisted failure messages are truncated at 2,000 chars** | A long `anyhow` chain — typically an upstream error that embeds a response body — loses its tail in `task_runs.last_error_message`. | Keeps the row bounded and cheap to print; the full chain is still in the logs (Cloud Logging for a deployed worker). | Triage needs the truncated part, or the message is the only surviving record of an upstream failure. |
| **No visibility into requests rejected before the container** | The edge can refuse a request (size, routing, quota) without writing any `cloud_run_revision` log. `resource.type="http_load_balancer"` returns nothing because load-balancer logging is off, and `dreamscroll.ai` front-ends the service through a Cloud Run domain mapping. An empty log query is therefore ambiguous: "no request arrived" and "the request died at the front door" look identical. | The front door has carried a three-user app without a suspected edge rejection; turning on and paying for LB logs is not justified yet. Cost this ambiguity once during the 2026-10-29 upload investigation. | A failure is reported that is absent from the revision logs, or a 4xx/5xx is traced to the edge. Then enable `logging.googleapis.com/load_balancing` or front the service explicitly. |
| **Backfill candidate relation shape is developer-managed** | Definitions must emit unique `entity_id`/`owner_id` rows without internal pagination. Duplicate rows waste batch slots; an inner limit can prevent progress to later targets. | Code-defined implementations use the shared `Backfill` contract and regression checks rather than a runtime query-AST validator or per-target tracking table. | Invalid candidate relations become a recurring implementation error or definitions stop being code-defined. |

### Illumination persistence

| Issue | Effect | Why tolerated | Revisit trigger |
| --- | --- | --- | --- |
| **No explicit active illumination head for reruns/backfills** | Concurrent or late results can surface according to existing per-route ordering instead of an intentional promotion. | Keep the initial persistence model to one entity table and existing result flow. | An overlapping re-run/backfill displays or indexes the wrong result. |
| **No atomic handoff from v2 persistence to vector indexing** | A crash after relational persistence but before the search task is enqueued can leave a capture unindexed; failed enqueue retries illumination and can append another v2 result. | An outbox/transactional handoff is beyond prototype scope; task retries usually recover. | A capture remains unindexed after retries or enqueue failures produce duplicate results. |
| **Legacy v1 illumination is raw-only** | Explicit v1 runs, including `dreamscroll_api illuminate --prompt-version v1`, store inference JSON/provenance but no relational illumination, knowledge-entity, or search-index content. | API/WebUI and REST requests default to v2; v1 remains available for evaluation of `illumination_raws` and emits a warning. | Before relying on a manually requested v1 result in the app. |
| **Legacy illumination rows may lack suggested searches** | Older rows can have `NULL` after suggested searches moved into `illuminations`; the UI now treats these as empty, so former `xqueries` suggestions are not migrated. | Avoid a data migration for prototype-local data; new v2 inserts always persist the list. | If old captures need their prior suggestions restored. |
| **Raw-only reruns leave projections and the search index on the prior run** | `persist_projection=false` writes raw output and usage metadata but preserves existing projections and skips indexing, so the newest raw result is not what the UI displays or search returns. | The mode exists for evaluation of prompts/model parameters; overwriting a good projection with an eval run would be worse. | Eval runs need to surface side by side with the live projection, or operators forget which run is live. |
| **Occurrence pages derive siblings from the capture's newest illumination** | The entity page reads the capture, not the occurrence's own `illumination_id`, so after a re-illumination an occurrence lists the siblings produced by the later illumination rather than the ones it was created with. | Sibling navigation is a browsing aid, not a historical projection; querying by the occurrence's illumination adds a second read path for a rare state. | Occurrence pages become a record of per-run output rather than a current-entity view. |

### Web UI and REST surface

| Issue | Effect | Why tolerated | Revisit trigger |
| --- | --- | --- | --- |
| **The archived feed is unlinked and unpaged** | `/archived` renders the user's archived captures, most recently archived first, capped at 100. Nothing in the header navigates there; the URL has to be typed. | Archive is a recovery surface, not a destination. A nav entry and a cursor would be spent before anyone uses the page. See `GET /archived` in `src/webui/v2/r_archived.rs`. | Archiving becomes routine, or the cap starts hiding captures someone wants back. |
| **Archive/unarchive is a plain form POST with a full page load** | The button lives in the card footer and posts `next` (a validated local path) so the user lands back where they clicked. No HTMX fragment, no optimistic toggle. | Cheapest thing that works and needs no JS; the same page renders the flipped button on reload. A fragment endpoint would have to re-render the whole detail card for one word. | Archiving becomes a bulk or high-frequency action. |
| **`GET /api/captures` cannot read an archived capture back** | The REST read goes through the same bulk loader as the feeds, which filters archived rows, so a client that archived a capture gets nothing for that id. The web UI can still open it by id. | The web UI is the only archive client today; `?include_archived=true` is API surface nobody has asked for. | A non-web client needs to reopen or list archived captures. |
| **The admin entity export serves another user's entity text** | `GET /api/admin/export/entities` pages over `user_observed_entities` for every user, `?user_id=` narrowing it to one — names, descriptions, platform handles, plus archived captures — deliberately bypassing the per-user scoping that `GET /api/entity/{id}` enforces. | It exists to run entity-resolution analysis offline against the real corpus; the gate is the JWT's `is_admin` claim, and the only client is the operator CLI (`dreamscroll_api export-entities`). | A non-operator client needs it, or it is reachable without the admin check. |
| **The entity export is paged JSONL, not one streamed response** | A 100k-row export is 100 requests at the 1,000-row default page (max 5,000); the next-page cursor travels in the `x-next-after-id` header. A client can stop or resume between pages, but a whole export is never one request. | Bounded pages keep each request inside the Cloud Run timeout, and the header cursor keeps the body pure JSONL without a trailer line. | Export size makes round trips the bottleneck, or a consumer needs a single streamed response. |

### Code cleanliness

| Issue                                                                    | Effect                                                                                                                                                                                                                                                       | Why tolerated                                                                                                                                                                                                                                                                                                                                              | Revisit trigger                                                                                                             |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **"Two-owner rule" is slightly aspirational**                            | Docs say only `TaskMaster` (writes) and `StatusListener` (reads) touch `task_runs`, but `TaskRunTracker` also touches it directly (shared by both).                                    | Harmless — the tracker is the shared persistence utility.                                                                                                                                                                                                                                                                                                  | If a third caller appears.                                                             |
| **Replay is a manual command, and `resolve` ignores the log** | A person's merges are re-applied only by `verdicts replay`. A rebuild that skips it leaves the graph on the model's opinion alone — the decisions are not lost, they sit in the log. | Keeping the sequencing explicit beat teaching `resolve` about verdicts, and the omission is visible: the pairs reappear as candidates. | Someone loses a decision to a rebuild they expected to keep it, or rebuilds become routine enough to script end to end. |
| **Scoring is a concrete heuristic, not a trait seam** | `Heuristic::link` / `merge` / `pair` are inherent methods; the linker holds one, the proximity passes are handed one. The resolver keeps its own measure and calibration because its candidates are private and its fit is corpus-aware. | The `Similarity`/`Policy`/`Rank`/`Scoring` bundle had exactly one implementation, so it was indirection over a unit struct. A second policy would reintroduce the seam; the measured-out trait version is in git history. | A second scoring policy is wanted, or the resolver's thresholds drift from the store's again. |
| **Schema 39 drops identities, claims and proximities** | Those three tables are derived; observations and `fetch_cache` survive. A database syncing to 39 rebuilds with `reset`/`link`/`resolve --offline`. | In-place reshaping (one identity row per claim, new unique key, new proximity shape) was more migration SQL than the data was worth. | Production data becomes too expensive to rebuild, or a migration must run unattended. |
| **An identity key can repeat across provider rows on one entity** | Two identity resolvers asserting `wikidata:Q42` are two annotations, with their own method and confidence. Stats count annotations; `query_entities_for_identity` dedupes entities. | Corroboration is real signal, and per-provider rows keep a resolver's replacement from deleting another provider's annotation. | A consumer needs one row per key and starts hand-deduping. |
| **A veto deletes identity annotations** | The annotation is derived; `knowledge_verdicts` is the durable decision, and replay re-applies it. There is no append-only retraction history within a generation. | The old `retracted_at` existed to suppress a re-derived edge; admission already suppresses the write, and full replacement made tombstones awkward. | Someone needs to audit a retraction's row history, not just the verdict. |
| **`MAX_CLAIMS_PER_ENTITY` is gone** | A resolver's output is trusted; the engine replaces the provider's set when it answers. An identity resolver could return many identities for one entity. | The resolver is ours, and the cap was policy for an agentic provider that does not exist yet. | A provider floods an entity, or an agentic resolver is wired in. |
| **`first_seen` is gone; `observed_at` remains** | Partial replacement cannot preserve a per-key first sighting without reading before deleting. `observed_at` records the annotation's write time. | No reader used `first_seen`; adding it back needs a per-key carry-over rule. | Someone needs "when did this entity first get this identity". |

## Resolved (kept for context)

Fixed because they were cheap, unambiguous, and didn't distract from product
work. Recorded here so the ledger is complete.

| Issue                                                                                      | Resolution                                                                                                                                                     |
| ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `task_runs` had no entity linkage                                                         | Added `entity_type` + `entity_id` (indexed) and the incomplete-status query APIs.                                                                              |
| `TaskRun` `Debug` could panic on a UTF-8 boundary                                          | Now takes a char-boundary-safe prefix.                                                                                                                         |
| Retry/exhaustion policy undefined (`attempts` hardcoded, `ErrorFinal` never written)       | Full policy: `task_max_attempts`, `ApiError::is_retryable()`, `AttemptOutcome`, and the ack-on-exhaustion HTTP mapping.                                        |
| `query_status` ignored `user_id`                                                           | Removed entirely (no callers).                                                                                                                                 |
| `background` always `false`                                                                | Field removed.                                                                                                                                                 |
| `ErrorWillRetry` returned `503`                                                            | Changed to `500` — `503` triggers Cloud Tasks *queue-wide* congestion throttling.                                                                              |
| `begin_attempt` could resurrect a completed task                                           | Now returns `None` for already-`CompleteSuccess` tasks, which the handler acks.                                                                                |
| Builder default `max_attempts` was 1                                                       | Now 3, mirroring the config default.                                                                                                                           |
| Assorted doc drift (`from_task` → `new`, stale "terminal" concept, `task_id` in examples)  | Corrected.                                                                                                                                                     |
| Postgres URL construction duplicated between `src/database` and `src/test_support/test_db` | Consolidated on `database::make_url_from_config`, which takes an optional schema. The harness now loads the app config instead of reading `DATABASE_URL`.      |
| `TaskRunTracker::record` was SELECT-then-INSERT, not an atomic upsert                      | Replaced by `insert_run` (insert, unique-violation → `Ok(false)`) + `set_status` (targeted update). Duplicate submission is now *refused*, not a DB error.     |
| Duplicate task submission could queue the same work twice                                  | Submit now reads the latest run and refuses if it is in flight. `(logical_id, run_number)` unique makes it race-safe.                                         |
| Reruns were indistinguishable from the original run                                        | Added the per-logical `run_number` plus globally unique `run_id`; settled runs append a new TaskRun instead of overwriting prior status.                          |
| `TaskStatusSnapshot` was a type that existed only to move two fields                       | Dropped; `query_status` returns the row (later split into `latest_run` / `query_run_status`), consistent with the other queries.                               |
| Stale-incomplete-run shadowing: a new completed run could be hidden by an older failed one | Incomplete queries collapse to the latest run *before* applying the incomplete predicate. Locked by the `completed_latest_run_hides_an_older_failed_run` test. |
| Idempotency guards in `logic/illuminate.rs` / `logic/search_index.rs`                      | **Deleted.** They were a cost optimization for duplicate work we tolerate, and the illuminate guard silently no-opped every rerun. Net LOC reduction.          |
| Reruns would have been served a stale illumination (`\| first` returned the *oldest*)      | `InfoMaker` collapses `illuminations` to the highest `id`, so `CaptureInfo.illuminations` is a single-element list by contract.                                |
| `google-cloud-aiplatform-v1` was used only for Vertex illumination | Removed; both Interactions backends now use the shared `reqwest` client and existing `google-cloud-auth`. The dependency is absent from `Cargo.toml` and `Cargo.lock`. |
| Task and TaskRun ownership was conflated with submitter identity | `Task` now carries `entity_owner_id`; `TaskRun` does not duplicate it, and `TaskRunTracker` persists it from the task. TaskMaster permits submission only by the target owner or an admin. Submitter tracking remains separate and is not implemented. |

## Pending — design trade-offs, not yet implemented

Recorded from `plan/archive/knowledge-canonical-entities.md` so the choice is not rediscovered later. Each
moves into the ledger above when its phase lands.

| Trade-off | Why acceptable now | Revisit trigger |
| --- | --- | --- |
| Aliases live in `core_knowledge_entities.aliases text[]`, with no provenance of their own. | Every surface the model wrote is still on its observation row, so provenance is recoverable by join. Blocking over ~2k cores per user is trivial. | Blocking slows above ~100k cores/user; or an alias needs to be audited on its own. |
| A merge **flattens**: it rewrites `user_knowledge_entities.core_id` and keeps `superseded_by_id` as a tombstone. | Supersession is 0.5% of prod, so the write is negligible and reads stay a single join. Unmerge reads the moved ids from the `merge` evidence row. | Merge rate above a few percent, or merges moving thousands of observations. |
| Two concurrent captures can create two provisional cores for the same referent. | The `unique (wikidata_qid)` / platform indexes convert the second resolution into a merge; until then the overlay shows two rows. | Duplicate rows become visible in the UI at scale. |
| The core carries no owner; a read starts at the viewer's observations and left joins. Disclosure policy is deferred to the read boundary rather than encoded in the schema. | A referent is not owned, and an owner column would contradict the cross-user merges the graph is for. Every attribute records its source, so a policy can be applied later without a write-path change. | Disclosure turns out to need a write-time constraint, or a read path stops starting at the viewer's observations. |
| A provisional core may merge across users, so two unverified hypotheses can become one row. | The merged row is still provisional — nothing is published on the strength of it — the merge is scored and reversible, and two independent captures agreeing is the signal the shared core exists for. | Provisional merges turn out to be wrong at a rate the unmerge path cannot absorb. |
| Pending candidates are a derived view, not rows. | An undecided hypothesis is recomputable from evidence plus the scorer; only accept (merge) and reject (`identity_rejection`) are stored, both append-only. | The review list gets slow, or the scorer becomes too expensive to run on demand. |
| Merge and score thresholds are constants, not yet calibrated. | The scoring model and feature set are settled; the numbers are pending the labelled measurement sheet. | Before phase 3 ships — thresholds must come from the sheet, not intuition. |
| `IdentityResolver::resolve` takes a **batch** of entities (`&[knowledge_entity::Model]`) rather than one. | Cross-entity batching is the difference between ~120 transport calls for a corpus walk and ~5,000 — at the 1s pacer, two minutes against eighty. Only the resolver knows how to group its own requests, so only the resolver can batch them. | A resolver needs genuinely per-entity control (an agentic one deciding case by case), or batching stops mattering because the corpus is small. |
| The fetch layer is its own **top-level module** (`src/fetch`), generic over each provider's request kinds and payload (`Transport::Kind` / `Transport::Payload`), so it names no provider and no knowledge entity. | Every rule it enforces — cache first, paced, budgeted — is provider-agnostic, and the associated types are what keep it that way: a provider's vocabulary cannot leak in because there is nowhere to put it. The cost is one type parameter on `Gateway::answers_for` and a `Display` bound on a provider's kind. | A second consumer wants the door without a `Request` (a streaming or paginated provider), or the associated types fight an agentic resolver whose "requests" are tool calls. |
| `resolution_cache` is renamed `fetch_cache` (schema 31), and its model with it. | It was kept for a reason that expired the moment the split landed: the table belongs to `crate::fetch`, which knows nothing about knowledge entities, and `resolution_cache` named a module that no longer exists. Deferring it was costing a reader the explanation every time, to avoid ten mechanical edits and a guarded rename. The eval replays were the stated obstacle; they are two `FROM` clauses. | Reverting this — a table name is one `ALTER TABLE`, so the cost of being wrong is small; the cost of the stale name is a footnote in every doc that mentions the cache. |
| A cached payload that no longer decodes is a **miss**, not an empty answer. | The payload is the provider's own type; when it changes, the row answers a question nobody is asking any more. A miss costs one refetch; an empty answer would stand for a week and look like a fact. | Decode failures turn out frequent enough to be a refetch storm — which would mean a `shape` was not bumped when it should have been. |
| A **cache-only run has no allowance** (`Gateway::new(cache, None)`) rather than an allowance that refuses every call. | "May never fetch" is a construction-time fact, so it belongs in the type: `Refusal` then holds only reasons that can arise mid-run (`Budget`, `RateLimited`), and the gateway carries no offline flag or branch. The engine still reports `offline` from its own options, which is where the operator asked for it. | A third *construction-time* reason appears — then it belongs in the type too, not in the enum. |
| A refusal **ends the walk** by default (`fail_fast: true` on `Gateway::new`), and `false` keeps reading the remaining groups' caches while fetching nothing more. | The cache is durable, so the groups a stopped run skips are read by the next run at no network cost — stopping is the honest default, and it keeps `Refusal::Budget` meaning "the run stopped here". Harvesting costs one wide `IN (…)` per remaining group (a group carries every query for its kind, thousands in a corpus walk), so it is worth doing only when the caller judges the warm cache worth more than those reads: a parameter, not a constant. | A third setting is wanted — stop after the current batch only, say — and the bool becomes a small enum. |
| An agentic resolver (`GeminiResolver`, not yet built) uses the cache by **convention**, not structurally: its tool calls happen inside the provider's runtime, where we cannot intercept them. | Routing them would mean exposing a callback endpoint with auth, a per-run id and idempotency — a lot of machinery for one resolver. Its claims still carry `provider = model` / `method = gemini`, so a guess is never mistaken for a citation. | Unaccounted agent lookups become a real cost, or the trajectory is needed for something other than debugging. |

| `KnowledgeGraph::merge` projects the winner **twice**: once inside `merge_in_transaction` (so the row it commits is already correct) and once after the commit, which is what tells the held blocker. | The second projection is idempotent and writes the same values; merges are 13 in the whole corpus, so the duplicate write is invisible. Doing the notification inside the transaction would be wrong the other way: a rollback would leave the index holding a row that never landed. | Merges become frequent, or a merge starts doing enough per-write work that the second projection is measurable. |
| The held `NameBlocker` knows only **this process's** writes. | Every mutation inside `Knowledge` notifies it — `project` for a change, `forget` for a discard or a tombstone — so a single writer per instance is exact. A second writer (the CLI against the same database, another Cloud Run instance) is invisible to it, which is a duplicate-entity risk the per-call rebuild did not have. Accepted because a link task is one writer per illumination and the alternative is the blocker below. The fix was a `SqlBlocker`, not a shorter TTL — shipped 2026-11-06: it reads `knowledge_blocking_index`, so it sees every committed row. The in-memory blocker held on only as the parity oracle, and was deleted 2026-11-07 once parity held with the handle probe added to both sides. | Two instances link different captures of the same referent and the corpus shows the duplicate; or linking is queued at a rate one instance cannot keep up with. |
| `knowledge_entities.origin_observation_id` has **no foreign key** to `user_observed_entities`. | The key would be circular — `user_observed_entities.knowledge_entity_id` already points this way — and observations are never deleted, so the reference cannot dangle; `project` falls back to the first member when it is null. | Observations ever become deletable, or an entity's origin needs to be enforced rather than trusted. |
| `merged_into_id` is **append-only**: a merge never rewrites another tombstone's pointer, so a chain can be more than one hop. | Append-only is what keeps unmerge a single pointer restore, and in practice a chain is one hop. Re-pointing would buy a one-lookup read and spend the audit trail. | A redirect walks more than two hops, or a read path starts assuming a single hop. |
| A duplicate identity is **prevented no longer**, only reconciled: `unique (knowledge_entity_id, knowledge_identity_id)` is the only uniqueness left. | Exclusivity was a duplicate detector, not a fact — one Wikidata item can name an album and cover its songs. Two claims on one identity used to fail at write time and trigger a merge; now both land and `proximity::auto_merge` asks whether the holders are one thing, which is where scoring belongs. The cost is a window in which two entities can hold one identity, and a merge for what used to be no-op. | Duplicates need a merge to be corrected (`merge` never folds them), or merges for look-alikes start showing up as tombstone churn. |
| Sharing an identity **does not merge**: `proximity::auto_merge` folds only holders that score as one thing by the linker's weights. | Identity equality was the wrong trigger — 6 of 8 corpus contradictions were cross-type (a character holding a film's item), and they merged silently. The scorer already knows the difference; the album case (a song holding its album's identity) is the same shape and must not merge either. Consequence: `contested` drops to zero for those pairs, because "the identity resolver's granularity disagrees with ours" is no longer a conflict. | A pair that is genuinely one thing keeps failing to score (names too different), so duplicates accumulate. |
| Expired resolution-cache rows are **pruned only after 30 days** (`PRUNE_GRACE`), on the next online resolve. | A stale row is invisible to reads and is only rewritten if the same query is asked again, so without a prune the table grows with every query ever made. Keeping a month past expiry means "we asked last week and the answer aged out" stays visible, which is how the two lost claims were diagnosed. | The table needs to be an audit of every question ever asked, or the grace window hides something that mattered. |
| A reset keeps only the newest **ten snapshot suffixes** and drops older archive tables. | Snapshots are tuning artifacts, not product data; thirty-five generations had accumulated 672 tables and half the database. Ten is enough to compare recent runs. The generation register still keeps its history. | A comparison needs a suffix older than the tenth; raise the constant or take an explicit export first. |
| `knowledge_blocking_index.text` is written but not read yet. | It is 41 kB and may become the full-text probe; removing it now would mean rebuilding the index later. It has no GIN index or reader, so it is explicitly not part of blocking today. | A full-text probe is built, or the column becomes a meaningful share of the index. |
| The proximity batch is **disposable, not a record**: `scan` deletes the table and re-derives it, so a row is "what the graph looked like when last asked" — no status, no history, no verdict column. | A flag on a derived row is a flag on a fact the next derivation re-creates, which is the same reason claims have no ids. What must survive a rebuild is a person's decision, and that lives in `knowledge_verdicts`: `merge` records every fold and `veto`/`replay` keep a person's answers, so a settled pair has no second holder left to re-raise it. | Someone needs "we looked at this pair and said no" to stick across scans — then the decision belongs in the verdict log, not on the row. |
| An observation's handle is **claimed after linking**, not before: the linker maps the observation's optional `PlatformLink` to an `IdentityKey`, reads an existing identity with `find_identity_id`, and falls through to scoring; `helper::write_observation_claims` settles and writes the observation's own afterwards (`claim_identity`, then project). | `Decision` is observation data and carries no identity id, so the executor has nothing to create before deciding, and every decision is made before any write. The cost is a silent one: two observations claiming the same *new* handle both create, and the pair they form can never be merged — `merge` refuses a shared illumination, so the scan keeps it as an open question. | A decision needs to know an identity this same batch will create; then the phase order has to change, not be patched. |
| A claimed identity **bypasses scoring**: a claim holder is attached to before candidates are scored, so a handle naming a stub wins over a name naming the real entity. | Accounts are the one case where the claim *is* the evidence — `@tsoding` and `Alexey Kutepov` share no name — and the 263 handle-only entities in the corpus were not created by the shortcut. | Stub-named accounts (`abcdent` ← `@abcdentminded`) start absorbing captures meant for a person entity; then the claim becomes a score term instead of a bypass. |
| Nothing stops a second observation of one illumination from taking the entity a sibling took: the same-illumination veto is gone from the linker. | Whether siblings are one thing is the scorer's question — it weighs name, description and type, where the veto weighed only "same image, therefore different", which is an assumption about extraction quality rather than evidence. It never fired on the corpus: removing it moved 0 of 2545 observations and the graph rebuilds identical (`compare`: 0 split, 0 merged, 0 moved). Its own failure mode was no better — a duplicate that `merge` refuses, so the scan can only record it. | A single capture folds two of its own subjects into one entity. That is a ranking bug, to be fixed with the scorer's evidence; add the veto back only once there is a measured failure to justify it. |
| Two observations of one illumination claiming one **new** handle become **two entities**, not one: decisions are all made before any write, so neither sees the other's claim. | The executor would otherwise carry an identity → entity map, which is policy in the layer that is supposed to be pure effect — a third home for the same-illumination rule after the decider's `claimed` set and `merge`'s `shared_illuminations` refusal. The case has never occurred (0 such illuminations in the corpus). Consequence: `merge` refuses the pair, so the scan records an open proximity that stays open. | The illuminator starts emitting one handle on two rows, or the open proximity shows up in a review list often enough to want an automatic answer. |
