# Pragmatism — tolerated trade-offs

**Status:** living document. Last updated 2026-10-23.

> **See also:**
> - `plan/archive/task-status.md` — the task framework (implemented).
> - `plan/archive/sse.md` — the implemented SSE delivery layer.
> - `plan/testing.md` — the two-tier test model.

## Philosophy

Dreamscroll is an exploratory  project whose primary risk is **not** technical.
The primary risk is that the app isn't useful enough to justify its own
existence. Every hour spent hardening a race condition that only manifests
under multi-user concurrency is an hour not spent validating the core use case.

So: **we deliberately tolerate a set of known issues** in order to move fast on
product validation. This document is the ledger of those trade-offs, so that:

1. We don't rediscover them repeatedly and re-litigate whether they matter.
2. We don't forget them — each entry has a **revisit trigger** describing when
   it stops being acceptable.
3. We can tell the difference between "we didn't notice" and "we chose this."

**The bar for tolerating something:** it must be primarily a *throughput, cost,
or code-cleanliness* concern, with no severe negative user-facing effect. If an
issue can corrupt user data, leak another user's data, or silently lose work in
a way the user would notice, it does **not** belong here — it gets fixed.

**The bar for fixing something now:** it's cheap, unambiguous, and doesn't
distract from product work. (Several items below were fixed on exactly that
basis and are recorded as resolved for context.)

## How to use this doc

- When you find an issue, ask: *does this have a severe user-facing effect?*
  - **Yes** → fix it, or file it as a real bug.
  - **No** → add it here with a revisit trigger, and move on.
- When a revisit trigger fires, promote the entry to a real task.
- When you fix something, mark it resolved rather than deleting it — the
  history of what we chose to tolerate is itself useful.

## Tolerated trade-offs

### Concurrency

These are all "correct at one user, wrong under concurrency." They are the
largest category, and the least urgent, because the app is single-user today.

| Issue                                                                        | Effect                                                                                                                                                                                                                                      | Why tolerated                                                                                                                                                                                                                                                   | Revisit trigger                                                                                       |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **No idempotency guards in `logic/illuminate.rs` / `logic/search_index.rs`** | A retry re-calls the LLM and may re-embed. Raw and relational illumination output upserts by TaskRun `run_id`, so sequential retries replace earlier output; overlapping deliveries may still duplicate inference cost or race to write. A new settled run has a new `run_id` and its own row. | Duplicate calls are accepted for prototype velocity. The read path surfaces the latest illumination, while TaskRun-keyed upserts prevent duplicate result rows for sequential retries. | Duplicate LLM spend becomes noticeable, or overlapping attempts write stale results. |
| **An in-flight search-index task can miss a newer illumination**             | If re-illumination occurs while indexing is in flight, that task may have already loaded the prior illumination. Beacon refuses a duplicate in-flight index submission, so the vector can remain stale until another index run or backfill. | Requires overlapping re-illumination and indexing; normal new-capture flow enqueues indexing only after illumination persists. A dirty/version marker or deferred rerun would add coordination state for a narrow race.                                         | A stale vector is observed after re-illumination, or re-illumination becomes a common operation.      |
| **Attempt claiming is read-then-write** | Concurrent deliveries can both execute; racing reads can claim the same attempt number, while a later `InProgress` redelivery may increment it. | Cloud Tasks is at-least-once; there is no atomic claim or lease fencing workers. Duplicate work and status races are accepted for the prototype. | Concurrent duplicates cause noticeable cost, incorrect status, or user-visible result ambiguity. |
| **Status transitions are permissive** | A late attempt can overwrite a newer status or run-keyed raw/relational output because updates are not fenced by attempt. | Duplicate overlap is possible, but strict transition/fencing logic adds lifecycle complexity; accepted for the prototype. | Out-of-order delivery produces visible incorrect status or raw output. |
| **Entity snapshot order is not a presentation contract**                     | The latest-run query orders rows by entity, task type, and descending run for PostgreSQL `DISTINCT ON`, not by UI presentation needs.                                                                                                      | Current consumers need the latest row per entity/task type, not a custom cross-entity order.                                                                                                                                                                    | The UI requires a different explicit ordering.                                                       |

> **Note on the removed guards:** the `illuminate` and `search_index` idempotency
> guards were deleted outright. A "skip if already illuminated" check silently
> no-ops every rerun (reporting success while doing no work), so keeping it meant
> deriving the run number from the illumination count — machinery that didn't
> reliably prevent the duplicate it existed for. Removing is simpler and makes
> reruns work by construction. A `UNIQUE(capture_id)` constraint on
> `illuminations` is *not* wanted: multiple illuminations per capture is the
> intended outcome of reruns.
>
> **Note on illumination visibility:** reruns append rows, so `InfoMaker` now
> collapses `illuminations` to the highest `id` — `CaptureInfo.illuminations` has
> at most one entry. This is enforced in one place rather than relying on loader
> order (SeaORM orders related rows by primary key *ascending*, so `.first()`
> would have returned the oldest).

### Cost / throughput

| Issue                                                                                                 | Effect                                                                                                                                | Why tolerated                                                                                | Revisit trigger                                                               |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **`api/user/client.rs` swallows `Beacon.new_capture` errors** (logs a warning, still returns success) | A capture can be uploaded but never illuminated/indexed, with no user-visible signal.                                                 | The upload itself succeeded, which is what the user cares about. Failure is visible in logs. | A user notices a capture that never got illuminated.                          |
| **`CloudTaskQueue` URL configuration is deployment-specific**                                         | The same `TASK_WEBHOOK_BASE_URL` must point to a reachable local host or public production origin, depending on the selected backend. | The queue backend is mutually exclusive, and one setting avoids duplicate configuration.     | A deployment needs separate task targets or URL validation becomes important. |
| **Inference usage persistence is best-effort** | Database insert failure or process termination can lose usage; successful outputs may have NULL `inference_meta_id`. Only TaskRun-backed requests are recorded, so direct CLI inference and inline query embeddings are excluded. | One shared warning-and-continue insert avoids retrying billable inference for bookkeeping. No recovery queue, outbox, or accounting-only TaskRuns. Raw usage remains available when the insert succeeds. | Missing usage becomes material for budgeting, or synchronous-query accounting is needed. |
| **Inference metadata cutover requires manual cleanup** | The operator drops obsolete metadata tables and removes old required bookkeeping columns from `illumination_raws`, or drops/recreates affected prototype tables, before running explicit schema sync. Historical bookkeeping may be discarded. | Prototype data needs no migration. Destructive cleanup stays manual rather than accumulating one-off DDL in `sync_schema`; model sync remains additive. | Historical metadata must be preserved, or staged/rolling schema compatibility is required. |
| **Historical inference JSON is not reclassified** | Rows written before request/provider separation may still contain response details in `params`; `provider_metadata` defaults to `{}` on existing rows. Data from the earlier version-4 provider-details column is not transferred. New rows use request-only params and separate provider metadata. | Prototype bookkeeping needs no data migration or compatibility branch; obsolete columns remain operator-owned cleanup. | Historical metadata must obey the new semantic contract for analysis. |
| **Related-capture previews are recomputed per detail-page view** | Each `/detail/{id}/related/previews` request fetches the source embedding and runs one vector search; nothing is cached or persisted. | The gallery is client-fetched after the detail page renders, so it never blocks first paint; results are cheap at prototype scale and staleness would be a new invalidation problem. | Related previews dominate detail-page latency or vector-search spend, or results must be stable across reloads. |
| **Entity-type listing is unbounded** | `get_entities_by_type` returns every matching row for the user with no limit or pagination, and the CLI taxonomy review relies on that shape. | Single user, and the endpoint exists for taxonomy review rather than interactive browsing. | The listing grows past a few hundred rows or gains a UI consumer. |
| **Thinking-level model compatibility is provider-validated** | The CLI/API accepts Gemini's four documented levels, but a particular model may reject a level it does not support. Omitting the override preserves provider defaults. | Avoid a stale local model-support matrix and silent effort downgrades while comparing inference behavior. | Provider validation errors become common enough to justify model-specific preflight checks. |

### Security / defense-in-depth

| Issue                                                                          | Effect                                                                                                                                                                                                                             | Why tolerated                                                                                                                                                                       | Revisit trigger                                                                                       |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **Task payload fields are not cross-checked against the stored run identity** | A malformed or stale Task can pair an existing `(logical_id, run_number, run_id)` with a different `entity_owner_id`, task type, entity, or payload; execution and SSE metadata could disagree with the submitted work. | Queue payloads are produced internally and the webhook has OIDC protection. Cross-checking payload fingerprints would add task-framework work while we validate the app's use case. | Enable another producer or observe a mismatched status/event. |
| **Worker update for a missing task-run row is warned and ignored**             | A stale or malformed TaskRun may execute without a matching status row; no SSE status event is sent for its update.                                                                                                               | TaskRun payloads are internal and authenticated; ignoring avoids retrying work whose tracking row is absent, while the warning keeps the inconsistency visible.                   | Observe a missing-row warning, or change stale-delivery policy.                                       |
| **Admin/internal Task owner is trusted** | A trusted admin or internal producer could set `Task.entity_owner_id` differently from the target row, misattributing status. | User submissions require the owner's Context; admin backfill reads the capture owner from the database; internal follow-ups copy the parent Task owner. Admin/internal producers remain trusted. | Add admin flows that accept arbitrary owner IDs, or observe a task/status owner mismatch. |
| **`TaskRunTracker::insert_run` is check-then-act**                             | Two concurrent submissions can both choose the same per-logical `run_number`.                                                                                           | The `(logical_id, run_number)` unique index arbitrates: the loser's insert becomes `Ok(false)`, so correctness does not depend on the read.                                    | If the refusal path is logged as an unexpected error, or a second user is added.                      |
| **Webhook OIDC verification depends on Google's JWKS endpoint**                | A cold instance or key rotation can add latency or temporarily fail webhook authentication if Google's certificate endpoint is unavailable. The Google crate caches each key for one hour, but does not retry a failed JWKS fetch. | `google-cloud-auth` provides maintained key fetching/caching; custom retry/backoff infrastructure is outside the MVP.                                                               | Authentication latency or task retries become operationally noticeable.                               |

### Operational

| Issue                                                 | Effect                                                                                                                                    | Why tolerated                                                                                            | Revisit trigger                                                                         |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **No retention / vacuum policy on `task_runs`** | The table grows forever. Note the run dimension means a reran task keeps *all* its rows, so growth is per-run rather than per-task.       | Tiny table, single user.                                                                                 | Row count becomes non-trivial, or query latency degrades.                               |
| **No heartbeat / timeout for stuck tasks**            | A task enqueued but never picked up (queue dropped, worker crash) stays `Queued` forever and looks active.                                | Requires an actual lost task, which hasn't happened.                                                     | First observed stuck task, or when the SSE UI makes it visible to the user.             |
| **No queue-level reconciliation**                     | The database cannot independently verify that a `Queued` row has a corresponding Cloud Task, or recover from an ambiguous enqueue result. | The app is small and the status row plus logs are sufficient operational visibility for the MVP.         | A task is observed stuck or missing, or Cloud Tasks/DB state needs auditing.            |
| **SSE heartbeat timeout is heuristic** | A delayed or suspended client can restart a healthy stream after 50 seconds without a heartbeat, adding a request and catch-up query. | The application heartbeat tells JavaScript that SSE events are still arriving; transport-level activity alone does not prove the browser received events. Background delivery remains best-effort. | Reconnects are observed on healthy delayed clients, or the 50-second detection window proves too long. |
| **SSE catch-up skips captures that already have an illumination** | Reloading a page during a re-illumination can miss the in-progress progress bar until the terminal event arrives. | Catch-up would otherwise query latest TaskRun state for every rendered capture on every page load and SSE connect. The reload-during-rerun flow is rare enough not to justify that DB load. | Reloads during reruns become common, or in-progress state during reruns becomes a product requirement; then batch/index the catch-up query. |
| **Blended feed treats `limit` as a per-source bound** | A blended timeline can return up to twice the requested limit (captures + sparks). | `limit` is currently an internal read bound; no UI exposes it, and total-feed semantics belong with the planned feed architecture work. | The feed gets explicit page-size/pagination controls, or membership/ordering is redesigned. |
| **Composite index on `task_runs` deferred**        | The entity snapshot query filters by user, entity type, and IDs, then selects the latest run per task type; only a single-column `entity_id` index exists. | Single-user app, tiny table. | Query latency degrades, or the table grows past a few thousand rows. |
| **Local queue shutdown is abrupt**                    | Dropping the final `LocalTaskQueue` handle aborts its dispatcher and drops pending in-memory tasks.                                       | The local backend is only for development and tests; production durability comes from Cloud Tasks.       | Local development needs restart-safe work or graceful shutdown testing.                 |
| **`submit_inner` records status before enqueueing**   | A process crash or ambiguous backend failure can leave a row at `Queued`; definite enqueue failures are changed to `SubmissionFailed`.    | DB-first submission avoids untracked tasks and duplicate execution; reconciliation can wait for the MVP. | A task is observed stuck or missing, or enqueue ambiguity becomes operationally costly. |
| **No explicit Gemini inference request timeout** | A stalled Developer API or Vertex call can keep an illumination worker occupied until the outer request/task deadline. | Defer client timeout behavior while validating the product; rely on existing outer deadlines for now. | A hung Gemini request causes task retries, duplicate spend, or delayed illumination; then set and test a client timeout shorter than the worker deadline. |
| **Undecodable notifications are skipped** | A malformed or future-schema NOTIFY payload is dropped; that hint never reaches clients and is only recovered by the next catch-up on reconnect. | The stream is best effort, and killing the fan-out loop for one bad payload would starve every user on the instance. | A real event kind is observed being dropped in practice. |
| **Backfill pumping can temporarily starve lower IDs** | A descending-ID batch occupied by live in-flight tasks is refused and remains eligible, so lower IDs can wait. | Live contention is expected to be short-lived and isolated; keep manual bounded pumps without cursor/scan-ahead/filtering machinery. | Contention or stuck live tasks persistently prevent progress. |
| **Backfill status counts actual runs, not expected workflow edges** | Beacon descendants inherit the ID, but refusal against unrelated live work creates no tagged child; aggregates cannot prove all expected descendants completed. | Avoid a dependency ledger and deferred follow-up scheduling. Same-backfill logical children are deduplicated, not counted per parent. | Operators need guaranteed end-to-end workflow completion. |
| **Backfill IDs and progress are developer-managed** | Reusing an ID after changing its definition or deleting tagged TaskRuns can invalidate progress. Failed tagged runs are not automatically replaced. | Stable literals and retained TaskRun rows avoid definition fingerprinting, migrations, and a per-target table. | Frozen membership, automatic recovery, or progress retention management becomes necessary. |
| **Persisted failure messages are truncated at 2,000 chars** | A long `anyhow` chain — typically an upstream error that embeds a response body — loses its tail in `task_runs.last_error_message`. | Keeps the row bounded and cheap to print; the full chain is still in the logs (Cloud Logging for a deployed worker). | Triage needs the truncated part, or the message is the only surviving record of an upstream failure. |
| **Backfill candidate relation shape is developer-managed** | Definitions must emit unique `entity_id`/`owner_id` rows without internal pagination. Duplicate rows waste batch slots; an inner limit can prevent progress to later targets. | Code-defined implementations use the shared `Backfill` contract and regression checks rather than a runtime query-AST validator or per-target tracking table. | Invalid candidate relations become a recurring implementation error or definitions stop being code-defined. |

### Illumination persistence

| Issue | Effect | Why tolerated | Revisit trigger |
| --- | --- | --- | --- |
| **No explicit active illumination head for reruns/backfills** | Concurrent or late results can surface according to existing per-route ordering instead of an intentional promotion. | Keep the initial persistence model to one entity table and existing result flow. | An overlapping re-run/backfill displays or indexes the wrong result. |
| **No atomic handoff from v2 persistence to vector indexing** | A crash after relational persistence but before the search task is enqueued can leave a capture unindexed; failed enqueue retries illumination and can append another v2 result. | An outbox/transactional handoff is beyond prototype scope; task retries usually recover. | A capture remains unindexed after retries or enqueue failures produce duplicate results. |
| **Legacy v1 illumination is raw-only** | Explicit v1 runs, including `dreamscroll_api illuminate --prompt-version v1`, store inference JSON/provenance but no relational illumination, knowledge-entity, or search-index content. | API/WebUI and REST requests default to v2; v1 remains available for evaluation of `illumination_raws` and emits a warning. | Before relying on a manually requested v1 result in the app. |
| **Legacy illumination rows may lack suggested searches** | Older rows can have `NULL` after suggested searches moved into `illuminations`; the UI now treats these as empty, so former `xqueries` suggestions are not migrated. | Avoid a data migration for prototype-local data; new v2 inserts always persist the list. | If old captures need their prior suggestions restored. |
| **Raw-only reruns leave projections and the search index on the prior run** | `persist_projection=false` writes raw output and usage metadata but preserves existing projections and skips indexing, so the newest raw result is not what the UI displays or search returns. | The mode exists for evaluation of prompts/model parameters; overwriting a good projection with an eval run would be worse. | Eval runs need to surface side by side with the live projection, or operators forget which run is live. |
| **Occurrence pages derive siblings from the capture's newest illumination** | The entity page reads the capture, not the occurrence's own `illumination_id`, so after a re-illumination an occurrence lists the siblings produced by the later illumination rather than the ones it was created with. | Sibling navigation is a browsing aid, not a historical projection; querying by the occurrence's illumination adds a second read path for a rare state. | Occurrence pages become a record of per-run output rather than a current-entity view. |

plan to do them properly."

## Resolved (kept for context)

Fixed because they were cheap, unambiguous, and didn't distract from product
work. Recorded here so the ledger is complete.

| Issue                                                                                      | Resolution                                                                                                                                                     |
| ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `task_runs` had no entity linkage                                                         | Added `entity_type` + `entity_id` (indexed) and the incomplete-status query APIs.                                                                              |
| `TaskRun` `Debug` could panic on a UTF-8 boundary                                          | Now takes a char-boundary-safe prefix.                                                                                                                         |
| Retry/exhaustion policy undefined (`attempts` hardcoded, `ErrorFinal` never written)       | Full policy: `task_max_attempts`, `ApiError::is_retryable()`, `AttemptOutcome`, and the ack-on-exhaustion HTTP mapping.                                        |
| `query_status` ignored `user_id`                                                           | Removed entirely (no callers).                                                                                                                                 |
| `background` always `false`                                                                | Field removed.                                                                                                                                                 |
| `ErrorWillRetry` returned `503`                                                            | Changed to `500` — `503` triggers Cloud Tasks *queue-wide* congestion throttling.                                                                              |
| `begin_attempt` could resurrect a completed task                                           | Now returns `None` for already-`CompleteSuccess` tasks, which the handler acks.                                                                                |
| Builder default `max_attempts` was 1                                                       | Now 3, mirroring the config default.                                                                                                                           |
| Assorted doc drift (`from_task` → `new`, stale "terminal" concept, `task_id` in examples)  | Corrected.                                                                                                                                                     |
| Postgres URL construction duplicated between `src/database` and `src/test_support/test_db` | Consolidated on `database::make_url_from_config`, which takes an optional schema. The harness now loads the app config instead of reading `DATABASE_URL`.      |
| `TaskRunTracker::record` was SELECT-then-INSERT, not an atomic upsert                      | Replaced by `insert_run` (insert, unique-violation → `Ok(false)`) + `set_status` (targeted update). Duplicate submission is now *refused*, not a DB error.     |
| Duplicate task submission could queue the same work twice                                  | Submit now reads the latest run and refuses if it is in flight. `(logical_id, run_number)` unique makes it race-safe.                                         |
| Reruns were indistinguishable from the original run                                        | Added the per-logical `run_number` plus globally unique `run_id`; settled runs append a new TaskRun instead of overwriting prior status.                          |
| `TaskStatusSnapshot` was a type that existed only to move two fields                       | Dropped; `query_status` returns the row (later split into `latest_run` / `query_run_status`), consistent with the other queries.                               |
| Stale-incomplete-run shadowing: a new completed run could be hidden by an older failed one | Incomplete queries collapse to the latest run *before* applying the incomplete predicate. Locked by the `completed_latest_run_hides_an_older_failed_run` test. |
| Idempotency guards in `logic/illuminate.rs` / `logic/search_index.rs`                      | **Deleted.** They were a cost optimization for duplicate work we tolerate, and the illuminate guard silently no-opped every rerun. Net LOC reduction.          |
| Reruns would have been served a stale illumination (`\| first` returned the *oldest*)      | `InfoMaker` collapses `illuminations` to the highest `id`, so `CaptureInfo.illuminations` is a single-element list by contract.                                |
| `google-cloud-aiplatform-v1` was used only for Vertex illumination | Removed; both Interactions backends now use the shared `reqwest` client and existing `google-cloud-auth`. The dependency is absent from `Cargo.toml` and `Cargo.lock`. |
| Task and TaskRun ownership was conflated with submitter identity | `Task` now carries `entity_owner_id`; `TaskRun` does not duplicate it, and `TaskRunTracker` persists it from the task. TaskMaster permits submission only by the target owner or an admin. Submitter tracking remains separate and is not implemented. |
